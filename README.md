# Energytool AI Consultant

Начальный прототип консультанта: веб-чат, поиск по локально переданной базе знаний, вызов совместимого API модели и локальное сохранение демонстрационных заявок. Исходные материалы организаторов и секреты в репозиторий не включаются.

## Демо

Пользовательский интерфейс: https://forgedev.ru. Краткий обзор архитектуры, сценария проверки ответа, управления базой знаний и ограничений демо: [PDF-презентация](output/pdf/MTS-Energytool-demo.pdf). Live-проверки и их ограничения: [отчёт стенда](docs/live-validation-2026-11-09.md); подтверждённый по исходному ZIP контракт сабмита: [описание контракта](docs/organizer-contract.md).

Скриншоты обновлённой страницы: [desktop](output/screenshots/user-page-desktop.png), [mobile](output/screenshots/user-page-mobile.png).

Дизайн-токены, компоненты и правила responsive/accessibility: [docs/design-system.md](docs/design-system.md). Общие CSS-токены находятся в `app/static/tokens.css`; стили чата и админки — в `app/static/index.css` и `app/static/admin.css`.

## Запуск

Скопируйте `.env.example` в `.env`. Шаблон настроен на DeepSeek (`https://api.deepseek.com`, `deepseek-flash`): добавьте свой ключ в `LLM_API_KEY`. Задайте длинные случайные разные значения `POSTGRES_PASSWORD`, `ADMIN_TOKEN`, `REVIEWER_TOKEN` и `RATE_LIMIT_SALT`. Для пароля PostgreSQL в Compose используйте буквы и цифры: специальные символы в URL соединения требуют отдельного кодирования. Создайте каталог `data` и положите в него предоставленный архив `knowledge-base.zip`. Запустите `docker compose up --build` и откройте http://localhost:8000. Сначала зарегистрируйте, утвердите и активируйте БЗ по инструкции ниже. Без настроенного API или активной БЗ возвращается безопасный ответ. Используйте только вымышленные контакты: заявки сохраняются в PostgreSQL и не отправляются.

DeepSeek используется для генерации и проверки claims. Для семантического канала поиска и reranker нужны отдельные совместимые endpoints; пока URL не заданы, приложение использует BM25.

Локально: `python -m pip install -r requirements-dev.txt`, `alembic upgrade head`, затем `uvicorn app.main:app --reload --no-proxy-headers`. Без `DATABASE_URL` используется SQLite `energytool.db`; переход на PostgreSQL не переносит существующие SQLite-данные автоматически. Тесты: `python -m pytest -q`. Для форматирования и статических проверок используйте `ruff check app core evaluation migrations tests package_submission.py solution.py`, `ruff format --check app core evaluation migrations tests package_submission.py solution.py`, `mypy --check-untyped-defs app core solution.py`, `bandit -q -ll -r app core solution.py` и `pip-audit -r requirements-dev.txt`. Для интеграционного теста PostgreSQL задайте `TEST_DATABASE_URL` и предварительно примените миграции к отдельной тестовой БД.

Состав 500 функциональных контрактных проверок описан в [docs/test-coverage.md](docs/test-coverage.md); adversarial сценарии и ограничения — в [docs/security-test-coverage.md](docs/security-test-coverage.md).

Для VPS используйте Docker Compose за reverse proxy с TLS: приложение опубликовано только на `127.0.0.1:8000`, PostgreSQL не имеет публичного порта, а контейнеры автоматически запускаются после перезагрузки Docker. Для корректного IP-based rate limiting задайте `FORWARDED_ALLOW_IPS` равным адресу Docker gateway, который виден приложению как peer reverse proxy, и настройте Nginx перезаписывать `X-Forwarded-For` значением `$remote_addr`. Оставьте HTTP для перенаправления и проверки ACME, обслуживайте интерфейс по HTTPS; задайте отдельные случайные секреты в `.env`, не добавляйте этот файл в Git и не проксируйте административные токены в URL. Настройте DNS A/AAAA перед выпуском сертификата. Для первой активации БЗ используйте административный интерфейс только по HTTPS.

Для VPS установите `ops/systemd/energytool-backup.{service,timer}` и `ops/systemd/energytool-restore-test.{service,timer}` в `/etc/systemd/system`, затем выполните `systemctl daemon-reload` и включите оба таймера. Резервная копия создаётся ежедневно в `/opt/energytool-assistant/backups`, содержит PostgreSQL и версии БЗ, хранится 14 дней с правами root-only. Еженедельный restore smoke восстанавливает последнюю копию во временную БД, сверяет схему и hash архивов, затем удаляет временную БД. После установки один раз запустите `energytool-backup.service` и `energytool-restore-test.service` вручную. Копии находятся на том же VPS и не заменяют off-site резервирование.

Answer-contract тесты используют поддельный OpenAI-совместимый gateway: проверяют деградацию на лексический поиск, цитаты и числа, отказ verifier и попытку внедрить инструкцию через БЗ. Это детерминированные контрактные проверки, а не измерение фактической точности конкретной модели.

Провайдер генерации задаётся независимо через `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`. Для отдельного теста с DeepSeek используйте `LLM_BASE_URL=https://api.deepseek.com`, свой ключ, `LLM_MODEL=deepseek-flash` и `LLM_JSON_MODE=1` для строгого JSON-формата claims/verifier ([официальный API JSON mode](https://api-docs.deepseek.com/guides/json_mode/)); в конфигурации оценочной платформы задайте требуемый ТЗ `qwen/qwen3.8-27b`. Для гибридного поиска отдельно задайте адреса совместимых API эмбеддингов и реранкера в `EMBEDDER_BASE_URL` и `RERANKER_BASE_URL` (при необходимости отдельные ключи и модели). Эти маршруты **не наследуются** от `LLM_BASE_URL`: без явно заданного endpoint соответствующий канал выключен. Поэтому конфигурация только с DeepSeek генерацией использует BM25 и не тратит время на неподдерживаемые retrieval-запросы. Ключи храните только в `.env`, не в Git.

Заявка создаётся в два шага: форма готовит черновик и показывает нормализованные контакты вместе с выдержкой из последних сообщений пользователя; только после подтверждения показанных данных создаётся запись. Повтор подтверждения с тем же `Idempotency-Key` возвращает прежнюю заявку. Черновик действует 15 минут; отмена удаляет неподтверждённый черновик. Истёкшие неподтверждённые черновики удаляются при подготовке новой заявки и фоновым заданием раз в час; подтверждённые заявки сохраняются. Для проверки браузера установите `requirements-dev.txt`, выполните `playwright install chromium` и запустите тесты с `RUN_E2E=1`.

Сообщения используют заголовок `Idempotency-Key` и поле `session_version`: повтор того же запроса возвращает сохранённый ответ, а устаревшая версия или повторное использование ключа с другим содержимым вызывает 409. Версию можно получить через `GET /api/sessions/{id}`, историю — порциями через `GET /api/sessions/{id}/messages?after_id=...&limit=...`. `POST /api/sessions/{id}/close` закрывает диалог для новых сообщений и заявок, сохраняя историю. Клиент сохраняет ключ неуспешной отправки в текущей вкладке и повторяет тот же запрос после обрыва.

Сессия хранит состояние жизненного цикла: `NEW`, `DISCOVERY`, `CLARIFYING`, `CONSULTING`, `LEAD_REVIEW`, `LEAD_CREATED` или `CLOSED`; `GET /api/sessions/{id}` возвращает его в поле `state`. Трасса содержит отдельно номера версий и переход состояния. Неподтверждённый черновик возвращается в предыдущее состояние после отмены или истечения срока. Новый вопрос отменяет черновик, чтобы старое подтверждение не относилось к обновлённому контексту. Остальные состояния из ТЗ (`RECOMMENDING`, `LEAD_OFFERED`, `LEAD_COLLECTING`, `ESCALATED`) пока не активируются: для них ещё нет подтверждённой маршрутизации и передачи специалисту.

## Управление базой знаний

Откройте http://localhost:8000/admin и введите токен администратора для регистрации, утверждения, активации и отзыва версий. Токен остаётся только в поле страницы. Регистрация и активация не заменяют ручную проверку документов: перед утверждением необходимо проверить полноту и правомерность использования. Файлы хранятся по хешу в `KNOWLEDGE_DIR`; перед использованием проверяется целостность. Кэш эмбеддингов привязан к содержимому.

Те же действия доступны через API с заголовком `Authorization: Bearer <ADMIN_TOKEN>`: `POST /api/admin/knowledge/register` регистрирует копию `data/knowledge-base.zip` и возвращает её SHA-256; `POST /api/admin/knowledge/{sha256}/approve`, `/activate` и `/revoke` управляют версией.

Каждый обработанный запрос чата возвращает `trace_id` (также `X-Request-ID`). Admin и reviewer могут открыть отладочную трассу на `/admin` или через `GET /api/admin/traces/{trace_id}`. Она показывает номера версий и состояния диалога до и после запроса, план поиска, число и идентификаторы evidence, факт проверки claims, модель/ревизию промпта, prompt/completion token usage (если endpoint его возвращает), общую задержку, причину fallback и активную ревизию БЗ. Текст пользовательского вопроса, сообщения и выдержки из БЗ в трассу не записываются; просмотр трассы аудируется. TTFT остаётся пустым: потоковая генерация ещё не реализована.

`GET /api/admin/knowledge` доступен также токену reviewer; `GET /api/admin/sessions/{session_id}/messages` возвращает reviewer только роли и длины сообщений, а admin — их текст. Действия с версиями и просмотр истории записываются в аудит без текста сообщений. Это ограниченный ролевой доступ по общим токенам окружения, без персональных учётных записей, ротации или раздельного утверждения. Храните токены вне исходников и не предоставляйте их посетителям.

## Ограничения и состояние сервиса

API ограничивает тело запроса 16 КиБ и частоту запросов в минутном окне: создание сессий, отправка сообщений и административные запросы — по 30 на адрес и категорию, остальные API — 120. Счётчики общие для экземпляров с одной БД и одинаковым `RATE_LIMIT_SALT`; при недоступности БД API отвечает 503. Значения `X-Forwarded-For` не используются для определения клиента; контейнер запускает Uvicorn с `--no-proxy-headers`. За общим прокси лимит применяется к адресу прокси, поэтому для промышленного размещения потребуется безопасно настроенный доверенный прокси или внешний ограничитель. Превышение лимита возвращает 429 и `Retry-After`. Одновременно обрабатываются не более четырёх запросов чата на процесс, сверх лимита возвращается 503. Это не глобальный лимит при нескольких процессах.

`GET /health/live` проверяет доступность процесса; `GET /health/ready` дополнительно проверяет соединение с БД, наличие утверждённой активной БЗ и конфигурации API модели. Последний endpoint не проверяет доступность удалённой модели. Страницы используют CSP без встроенных скриптов, а API и страницы отдают запрет кэширования. Эти меры не заменяют TLS и аудит безопасности.

Для сетевых вызовов настроен общий расчётный бюджет 25 секунд с отдельными лимитами на эмбеддинги, реранкер, генерацию и проверку; если основание или проверка недоступны, возвращается безопасный ответ. Таймауты HTTP ограничивают ожидание сетевых операций, но не являются гарантированным SLA и не включают всё время CPU или ожидания блокировки сессии.

## Сабмит

Пример организаторов задаёт `DATA_DIR/questions.csv` (`id,question`) и `DATA_DIR/knowledge-base.zip` (Markdown/TXT), результат — `submission.csv` (`id,answer`). Адаптер также принимает перечисленные в примере альтернативные имена файлов. Запуск: `python solution.py`. В entry point сабмита общий API base (`LLM_BASE_URL`, `BASE_URL` или `OPENAI_BASE_URL`) по умолчанию используется также для `/embeddings` и `/rerank`, как в примере платформы. Чтобы отключить конкретный канал или задать отдельный сервис, установите `EMBEDDER_BASE_URL` и/или `RERANKER_BASE_URL` явно; пустое значение отключает канал. Это поведение не применяется к веб-приложению: его retrieval endpoints настраиваются отдельно, поэтому конфигурация DeepSeek остаётся BM25-only. Команда `python package_submission.py` создаёт ZIP из кода и зависимостей; база знаний, вопросы и ключи в архив не входят. Тест `tests/test_submission.py` распаковывает этот ZIP в чистый каталог и запускает его на синтетическом наборе. Перед финальной отправкой отдельно сверьте лимиты ресурсов, доступность внешней сети и скрытые ограничения платформы: демонстрационный пакет их не определяет.

## Офлайн-оценка поиска

Запустите `python -m evaluation.retrieval_eval`. Скрипт сравнивает извлечённые документы с ручной разметкой в `evaluation/gold_sources.json` и сохраняет ранги в `docs/retrieval-baseline.json`. Диалоговый запрос формируется по пользовательским репликам, без реплик ассистента, затем расширяется ограниченными доменными синонимами. BM25 использует префикс токена длиной 5, `k1=0.7`, `b=0.25`; написания SIM-карты и фотографии нормализуются. На 18 вопросах и 292 фрагментах source-level recall@1 — 0,89; recall@5/10 — 1,00; MRR@10 — 0,94. Групповая кросс-валидация по первичному источнику даёт MRR@10 0,89 на 12 отложенных группах. Этот набор использовался при разработке правил расширения запросов, поэтому результаты исследовательские, а не независимый release gate; нужен отдельный holdout.

Для оценки конкретных доказательных фрагментов выполните `python -m evaluation.chunk_eval`. `evaluation/gold_chunks.json` связывает запрос с ручными evidence-якорями внутри файлов; если один факт подтверждают несколько равноценных фрагментов, укажите их в `alternatives` внутри одной записи. Каждый якорь проверяется при загрузке разметки, отсутствующие или устаревшие завершают оценку ошибкой. Текущий BM25 результат на 18 запросах, 292 фрагментах и 19 якорях: query-hit@5/@10 — 1,00; evidence-recall@5/@10 — 1,00; MRR@10 — 0,89. Отчёт сохраняется в `docs/chunk-retrieval-baseline.json` с SHA-256 архива БЗ, вопросов и разметки. Набор пока мал и оценки описательные: они проверяют lexical retrieval, не фактическую точность генерации, embeddings, reranker или полноту ответа.

Для HTTP latency baseline запустите `python -m evaluation.runtime_benchmark --requests 20 --concurrency 4 --output docs/local-api-baseline.json` при работающем Compose. Probe использует только синтетические запросы, закрывает созданные сессии и сохраняет commit SHA вместе с p50/p95/p99. При `service_readiness=false` результат измеряет только fallback-путь и API/БД, а не полный ответ модели; не сравнивайте его с KPI-12 до настройки разрешённого endpoint.

## Статус и ограничения

Сопоставление тестов с 20 классами атак ТЗ и ограничения red-team набора: [docs/security-test-coverage.md](docs/security-test-coverage.md).

Это **демонстрационная, не промышленная система**; публичный стенд `forgedev.ru` предназначен только для фиктивных данных. Поиск объединяет BM25 и эмбеддинги через reciprocal rank fusion и при доступности использует реранкер. При отказе эмбеддера или реранкера поиск продолжается по доступным каналам. Ответ проходит проверку структуры, точности цитат и чисел; точные числа из вопроса могут использоваться только как вводные объекта и отдельно передаются verifier без исходного текста пользователя. Перед генерацией есть консервативная проверка найденных фрагментов: близкие по формулировке утверждения с разной полярностью или числовыми значениями приводят к безопасному отказу. Она не распознаёт произвольные семантические конфликты и не задаёт приоритет документов; для этого нужна утверждённая владельцем БЗ политика. Отдельный вызов модели проверяет, следует ли утверждение из цитаты и вводных: он допускает смысловой пересказ, но сохраняет проверку существенных условий, отрицаний и направлений сравнений. `VERIFIER_MODEL` позволяет выбрать отдельную модель; по умолчанию используется генератор отдельным вызовом, поэтому проверка не является независимой. Детерминированная проверка чисел и единиц не заменяет семантическую проверку условий, а модель-проверяющий тоже может ошибаться. Нет персональной аутентификации. Целевые показатели точности и отказов не измерены на независимой разметке; ограниченный latency smoke описан в отчёте и не является SLA. Перед использованием закрытой БЗ с внешним API нужно разрешение владельца данных.

Конкурсный адаптер обрабатывает строки CSV независимо; многоходовый transcript передаётся внутри поля `question`, что подтверждено примером организаторов. Необходимо выполнить независимую экспертную оценку, нагрузочные и chaos-испытания, проверить права на данные и лимиты runtime, подготовить финальную инструкцию и согласовать доступ жюри.
